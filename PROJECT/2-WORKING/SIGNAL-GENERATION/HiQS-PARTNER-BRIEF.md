# Rebalance / HiQS — Partner Brief

*Audience: prospective partner · medium-level overview · 2026-06-13*

**The project.** Rebalance (codename HiQS, "High-Quality Signals") is a local-first personal-operations engine that ingests a developer-operator's scattered work signals — Google Calendar, GitHub activity, Slack/Sleuth reminders, email, and notes — into a single local database and answers one question: *"what should I work on next, and what's about to get dropped?"* The guiding thesis is that a new data source is only worth ingesting if it measurably raises *decision* quality, not just adds more text to read. Everything runs on the operator's own machine with a privacy-default-deny posture, exposed both as a web dashboard and as callable tools an AI agent can use. The core bet is that a busy operator's bottleneck isn't information — it's deciding which of fifty competing threads actually deserves the next hour.

**The team-work signal engine.** The newest module extends that engine from "me" to "the team" by blending a teammate's shared work calendar into the operator's own signal set. The pipeline is four stages: ingest each person's events (tagged by source and person), attribute each event to a shared project/client/repo, score every candidate next-action, then rank and surface the top items with who-owns-what attribution. We validated the idea *before* productizing it via a pre-registered, blinded A/B test — Arm A is the operator's own signals, Arm B adds the teammate's calendar — judged independently by the operator and an LLM judge across five days. The treatment passed a conjunctive three-metric gate (additivity, confirmed "dropped-ball" catches, and blind preference), surfacing real, actionable work the operator's own data structurally could not see (e.g. a delegated production-DB task and a blocked deployment).

**How the ranking works (the math).** Ranking is a transparent weighted-sum scorer, not a black box — closer to Taskwarrior's urgency model than a neural net — where each candidate action's score is a linear combination of tunable coefficients we call *levers*. The key levers are per-person trust weight, per-source weight, a *redundancy penalty* that down-weights any teammate item already echoed in the operator's own data (the "additivity" term), a vagueness discount, and an *owner-bias correction* that up-weights operational/client work the operator's own stream structurally under-represents. Formally, additivity is the fraction of teammate work-blocks that map to a shared project **and** have no corresponding signal in the operator's own data that day; the spike measured a median of ~58%, well above the 20% kill threshold. Defaults are seeded from the validated spike, so the decision rule it confirmed — *"prefer the teammate signal when my own data structurally can't see it"* — becomes the starting coefficients and then stays operator-tunable.

**The moat.** The moat is not the plumbing — local database + calendar/GitHub/Slack/email connectors + an agent interface is now a commodity pattern, and an independent survey of ~40 open-source projects found several converging on exactly that substrate. What no one else has built is the scoring brain on top: a tunable, *explainable* model that separates net-new from redundant signal, blends a team dimension, and flags delegated work about to be dropped. The defensibility compounds because the highest-value training signal — a ground-truth log of which commitments were actually *completed* versus quietly *dropped*, including delegated ones — exists in no public corpus and can only be self-generated from the operator's own outcome history. In other words, the data exhaust that makes the prediction engine better is proprietary by construction, so the model's edge widens with use rather than being copyable from a repo.
