### 1. ANSWER
We recommend **SKIP** for the first three patterns (Composition Layering, `capabilities/` Overlay, and Cross-Runtime Portability via Installer) to avoid over-engineering and premature abstractions, and **ADAPT** for the remaining two patterns (Read-Before-Edit Hook Guard and the Help/Index Skill) to improve runtime safety and discoverability.

***

### 2. GRADED FINDINGS
*   **[Should] Pattern 4 (Read-Before-Edit Hook Guard):** Adopt a PreToolUse read-before-edit check adapted from `gsd-read-guard.js` for Rebalance. LLM agents frequently fail to read files prior to editing, causing hallucinated edits and loop errors; a validation guard closes this gap cheaply.
*   **[Should] Pattern 5 (Help/Index Skill):** Adapt the help command index format from `commands/gsd/help.md` to both targets. Agents have no discoverability index for custom skills/commands in Rebalance or XYZ, causing token-wasting directory lookups.
*   **[Pass] Pattern 1 (Layered Composition):** Layered command-to-workflow-to-agent composition is a heavy abstraction built for multi-runtime and multi-agent systems; a flat markdown catalog natively suits the targeted runtimes.
*   **[Pass] Pattern 2 (`capabilities/` Layer):** The declarative capability overlays are designed to solve multi-runtime adaptation and dynamic plugin trust. Reb/XYZ do not run a modular runtime engine, making this abstraction a clear YAGNI violation.
*   **[Pass] Pattern 3 (Cross-runtime Portability):** Install mechanics/versioning belong in the out-of-scope installer family; details are punted to a pointer note in [GH-102](file:///Users/noelsaw/Documents/rebalance-OS/PROJECT/2-WORKING/GH-102-XYZ-REBALANCE-INTEGRATION.md).

***

### 3. RECOMMENDATION
Implement a lightweight read-before-edit PreToolUse hook for Rebalance and a discoverability `/reb-help` / `/xyz-help` skill index for both platforms to improve reliability and ergonomics without changing directory flat structures.

### 4. PATTERN-BY-PATTERN GRADING

#### Pattern 1: Skill ↔ Agent ↔ Command ↔ Hook Composition
1.  **The Gap:** `gsd-core` splits custom commands, workflows, agent roles, and hooks into distinct multi-file tiers ([docs/ARCHITECTURE.md:31-66](file:///Users/noelsaw/Documents/GH%20Repos/gsd-core/docs/ARCHITECTURE.md#L31-L66)), whereas Rebalance and XYZ use flat, self-contained markdown catalogs ([.claude/skills/welcome/SKILL.md:1](file:///Users/noelsaw/Documents/rebalance-OS/.claude/skills/welcome/SKILL.md#L1)) and command wrappers.
2.  **Call:** **SKIP**
3.  **Target:** Both | **Effort:** S | **Payoff:** 1
4.  **Why:** A flat skill catalog is natively supported, easier to discover, and avoids the heavy token load of parsing multiple files per invocation in single-runtime environments.

#### Pattern 2: The `capabilities/` Layer
1.  **The Gap:** `gsd-core` defines a central registry and overlay loader to inject capabilities dynamically into extension points ([docs/explanation/capability-overlay-model.md:18-41](file:///Users/noelsaw/Documents/GH%20Repos/gsd-core/docs/explanation/capability-overlay-model.md#L18-L41)), whereas Reb/XYZ execute static script pipelines without a dynamic runtime loop host.
2.  **Call:** **SKIP**
3.  **Target:** Both | **Effort:** L | **Payoff:** 1
4.  **Why:** Neither target has a multi-runtime adaptation or third-party plugin ecosystem to justify the high complexity of a dynamic capability-overlay engine (YAGNI).
