# Task: Integrate ask-self into This Repo

## Background

I maintain a developer tool called **ask-self**. It is a repository-grounded RAG system for code and docs: it ingests a repo, chunks source and documentation intelligently, stores embeddings in a per-repo SQLite database, and lets me query that indexed corpus with natural-language questions.

Current canonical ask-self repo:

- Location: `/path/to/ask-self`
- Main entry points:
  - `ask_self_ingest.py`
  - `ask_self_query.py`
  - `ask_self_harness.py`
  - `ask_self_system_instructions.json`
- Harness templates currently live at the **repo root**, not in a nested `ask_self/` package directory:
  - `wp_theme_harness.json`
  - `wp_plugin_harness.json`
  - `js_ts_generic_harness.json`
  - `ask_self_harness.json`
- Internal runtime defaults may still assume `ask_self/ask_self_harness.json` and `ask_self/ask_self_system_instructions.json` for copied-in integrations, so external wrappers should always pass an explicit `--harness-config` instead of relying on ask-self's defaults.
- Shared registry:
  - `temp/rag/ask_self_registry.json`

Current credential resolution order for Gemini:

1. `GOOGLE_API_KEY`
2. `GOOGLE_API_KEY_FILE` or `ASK_SELF_GOOGLE_API_KEY_FILE`
   - supports either a raw key text file or a small env-style file
3. `gcloud secrets versions access latest` when `GOOGLE_API_KEY_SECRET_NAME` or `ASK_SELF_GOOGLE_API_KEY_SECRET` is set
   - optional project override: `GOOGLE_API_KEY_SECRET_PROJECT` or `ASK_SELF_GOOGLE_API_KEY_SECRET_PROJECT`

ask-self is intentionally multi-repo. Each target repo gets a thin local integration layer:

- a local harness config
- local system instructions
- thin wrapper scripts that call the external ask-self install
- agent guidance so future AI sessions know the tool exists

Recent ask-self behavior that matters for integration:

- Ingest can generate a repo-root `ARCHITECTURE.md` automatically.
- Generated architecture docs now include:
  - a deterministic file inventory
  - a symbol index
  - a lightweight dependency map
  - freshness metadata
  - an optional Gemini-written "How it fits together" section
- If Gemini truncates the narrative, ask-self now:
  - retries with a more compact prompt once
  - falls back to a deterministic local narrative if needed
- If `ARCHITECTURE.md` was previously generated by ask-self, ingest now:
  - backs it up to `ARCHITECTURE-BAK.md`
  - overwrites `ARCHITECTURE.md` with the fresh version
- Generated helper docs such as `ASK_SELF.md` and `ARCHITECTURE-BAK.md` should generally be excluded from future ingests.
- Current runtime caveats:
  - `ask-self query` still requires `GOOGLE_API_KEY` for Gemini synthesis, even if retrieval uses local embeddings.
  - `qwen-local` requires `sentence-transformers` in the Python environment running ask-self.
  - `ask-self ingest` currently still expects `GOOGLE_API_KEY` to be present, even when the harness embedding provider is `qwen-local`.

## Goal

Wire ask-self into **this repo** so I can:

1. Run ingest to build or refresh a RAG index of this repo.
2. Run query to ask grounded questions with citations.
3. Register this repo's index in the shared ask-self registry.
4. Make future AI coding agents discover ask-self automatically through `AGENTS.md` and any existing parallel agent-instruction files.

## Detection Step

Before writing files, inspect the repo and determine which harness template is the best starting point.

Use these heuristics:

- `style.css` plus `theme.json`, or a theme-like layout under `wp-content/themes/`
  - Treat as a **WordPress theme**
  - Start from `wp_theme_harness.json`
- A root-level PHP file with a `Plugin Name:` header, or a plugin-style `readme.txt`
  - Treat as a **WordPress plugin**
  - Start from `wp_plugin_harness.json`
- `package.json` with TS, React, Next, Vite, Supabase, or similar signals
  - Treat as a **JS/TS project**
  - Start from `js_ts_generic_harness.json`
- `pyproject.toml`, `setup.py`, `requirements.txt`, or a clearly Python-first repo
  - Derive a harness from `ask_self_harness.json`
- Anything ambiguous
  - Ask me before finalizing

Also inspect:

- top-level repo layout via `ls -la`
- whether `ask_self/` already exists in the target repo
- whether `temp/rag/` already exists
- current `.gitignore`
- `composer.json`, `package.json`, `pyproject.toml`, etc.
- existing agent files:
  - `AGENTS.md`
  - `CLAUDE.md`
  - `.cursorrules`
  - `.augment/`

## Requirements

### 1. Keep ask-self external

Do **not** vendor, copy, symlink, or submodule ask-self into the target repo.

The integration should be a thin local layer that points to the external ask-self install via:

- `ASK_SELF_PATH`
- optionally `ASK_SELF_PYTHON` if the external ask-self checkout should run under a specific Python interpreter

Default it to:

- `/path/to/ask-self`

Allow override through the environment.

For credentials, recommend that new users store the Gemini key in Google Secret Manager rather than a committed or long-lived local file.

### 2. Create a local `ask_self/` directory in the target repo

This local folder is the integration layer for the target repo, not a vendored copy of ask-self.

Create:

- `ask_self/ask_self_harness.json`
- `ask_self/ask_self_system_instructions.json`
- optionally a tracked `ask_self/index/` directory when the repo wants a committed lightweight shared index

#### `ask_self/ask_self_harness.json`

Copy the most appropriate template from the external ask-self repo and tune it to the actual target repo.

Update at minimum:

- `repo_label`
- `repo_kind`
- `db_filename`
- `tenancy_env_var`
- `ingest_command`
- `github.owner`
- `github.repo`
- `shared_index`

Tune carefully:

- `docs.include_patterns`
- `docs.exclude_patterns`
- `source.include_patterns`
- `source.exclude_patterns`
- `classification_rules`

Important:

- Verify the regexes against real files before finalizing.
- Do not guess patterns that match nothing.
- Exclude generated ask-self docs if they would pollute future ingests:
  - `ASK_SELF.md`
  - `ARCHITECTURE-BAK.md`
- Decide deliberately whether `ARCHITECTURE.md` itself should be indexed for this repo.
- If the repo wants a committed team-shared baseline index, set `shared_index.enabled: true` and point `shared_index.path` at a tracked location such as `ask_self/index/<repo>-shared.sqlite`.
- Recommended default: `shared_index.prefer_for_query: false` so fresh local temp indexes still win when present.

#### `ask_self/ask_self_system_instructions.json`

Copy the current canonical file from the external ask-self repo and make the smallest repo-identity edit needed, typically in `base_system`.

Everything else should stay close to upstream unless the repo genuinely needs different answer behavior.

### 3. Create thin wrapper scripts

Create:

- `scripts/ask-self-ingest.sh`
- `scripts/ask-self-query.sh`

Or use the repo's existing script location if there is a stronger local convention.

Each wrapper should:

- resolve `ASK_SELF_PATH`
- default it to `/path/to/ask-self`
- resolve `ASK_SELF_PYTHON` if provided
- otherwise prefer `"$ASK_SELF_PATH/.venv/bin/python"` when it exists
- otherwise fall back to `python3`
- fail loudly if the external repo or entry points are missing
- invoke the external entry points through Python, not as executable scripts:
  - `"$PYTHON_BIN" "$ASK_SELF_PATH/ask_self_ingest.py"`
  - `"$PYTHON_BIN" "$ASK_SELF_PATH/ask_self_query.py"`
- pass `--harness-config` pointing at the target repo's local `ask_self/ask_self_harness.json`
- pass through additional CLI args unchanged

Keep the wrapper logic simple so it can later swap from path-based invocation to a packaged CLI with minimal edits.

If the target repo uses a committed shared index, wrappers do not need custom query fallback logic. ask-self query will automatically use `shared_index.path` when the local temp DB is missing.

For index placement, keep the distinction explicit:

- full local working indexes belong under `temp/rag/*.sqlite` and stay gitignored
- lightweight shared baseline indexes belong in a tracked repo path such as `ask_self/index/<repo>-shared.sqlite`
- do not replace the local temp index path with the shared tracked path; they serve different purposes

### 4. Update `.gitignore`

Add entries for:

- `temp/rag/`
- `temp/ask-self-rag.env`
- any other target-repo temp artifacts produced by ask-self

Do not over-broaden ignores if the repo already uses `temp/` for unrelated tracked content.
Do not ignore `ask_self/index/*.sqlite` if the repo intends to commit a shared baseline index.

### 5. Update README

Add a short section such as:

Include:

- one-sentence explainer of ask-self
- how to ingest:
  - `./scripts/ask-self-ingest.sh`

  - `./scripts/ask-self-ingest.sh --shared-index --mode all`
- how to query:
  - `./scripts/ask-self-query.sh "your question here"`
- note that `ASK_SELF_PATH` can be overridden
- note that credentials can come from `GOOGLE_API_KEY`, `GOOGLE_API_KEY_FILE`, or Google Secret Manager via `GOOGLE_API_KEY_SECRET_NAME`
- note that query prefers a fresh local temp index when present and otherwise falls back to the committed shared index if configured
- optional note that all indexes reflect the last ingest, not current uncommitted changes

## Architecture Doc Notes

If the target repo uses ask-self's automatic architecture generation, be aware of the current behavior:

- ingest writes `ARCHITECTURE.md` by default unless `--no-architecture-md` is used
- generated docs carry an ask-self ownership marker
- if an existing `ARCHITECTURE.md` is ask-self-managed:
  - it is renamed to `ARCHITECTURE-BAK.md`
  - a fresh `ARCHITECTURE.md` is written
- if an existing `ARCHITECTURE.md` is **not** ask-self-managed:
  - ask-self falls back to writing `ASK_SELF.md`
- the generated architecture doc now includes:
  - file inventory
  - symbol index
  - dependency map
  - freshness block
  - "How it fits together" narrative
- if Gemini truncates that narrative:
  - ask-self retries once with a compact prompt
  - if that still fails, it writes a deterministic local narrative instead of leaving the section blank

If you integrate ask-self into a target repo, make sure the harness excludes do not cause those generated docs to recursively pollute the index unless that is explicitly wanted.

## Shared Index Notes

If the target repo wants a committed shared index:

- treat it as a lightweight baseline for onboarding and agent startup speed
- keep the full local working index in `temp/rag/*.sqlite`
- keep the lightweight shared baseline index in a tracked path such as `ask_self/index/<repo>-shared.sqlite`
- prefer `--shared-index --mode all` so code and docs are both represented
- let local temp indexes win when present
- do not register the shared index in the multi-repo registry
- do not commit sibling cache or events files next to it
- expect the shared index to be somewhat stale between refreshes

## Migrating Older Integrations

If the target repo already has an older ask-self integration, do not rebuild it from scratch blindly. Normalize it to the current model:

- keep or add a local integration folder at `ask_self/` with `ask_self_harness.json` and `ask_self_system_instructions.json`
- keep full local working indexes in `temp/rag/*.sqlite`; that remains the right place for fresh per-user or per-branch ingests
- if the repo wants a committed team baseline, add a `shared_index` block and place that light shared index in a tracked path such as `ask_self/index/<repo>-shared.sqlite`
- update legacy wrappers so they always pass `--harness-config`, resolve `ASK_SELF_PYTHON` or `"$ASK_SELF_PATH/.venv/bin/python"`, and invoke ask-self through Python
- keep `temp/rag/` gitignored; do not newly ignore `ask_self/index/*.sqlite` if the repo intends to commit the shared baseline
- if an older repo previously committed an index under `temp/rag/`, move that practice to `ask_self/index/` instead and regenerate it with `./scripts/ask-self-ingest.sh --shared-index --mode all`
- if an older repo only had local temp indexes and no committed baseline, that is still valid; adding `shared_index` is optional, not mandatory
- do not register the committed shared index in the multi-repo registry; registry entries are still for local/full working indexes

## Future-Proofing

When ask-self eventually becomes a package or installable CLI, the desired migration path is:

- keep local harness files
- keep local system instructions
- keep README and AGENTS guidance
- only swap the wrapper invocation layer

So structure the wrapper scripts to make this future replacement small and obvious.
